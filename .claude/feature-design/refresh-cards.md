# refresh-cards: design

Spec: `claude-workspace/specs/gcg-toolkit/refresh-cards/spec.md` (PersonalClaude workspace)

## Approach
A new command, `gundam_cards refresh [--dry-run] [--allow-anomaly]`, runs one function, `refresh.refresh_catalog`, in three phases: **fetch**, **plan**, **write**. Nothing touches the dataset until the plan is complete, checked and accepted, so a refused run, or one that fails or is interrupted before the write phase, leaves it byte-identical. The write phase is a short series of atomic file writes (see Write and Risks).

**Fetch (light on Bandai).** Everything goes through the existing `shared.fetch.Fetcher` (descriptive User-Agent, one request at a time, at least 0.5 s apart, responses cached in the git-ignored `tools/gundam_cards/data/raw/`). The package list is Bandai's own: the package filter on the card page plus the product list pages (names, codes, release dates), parsed by the existing `sets.py` parsers; then every package's card listing, always fresh. A detail page is requested only when it is not cached yet, and never again after that. The fetching stops at the first failure: a failed request, a package list with no packages, a listing with no printings (unreadable), or a newly fetched detail page that `parse_detail_html` cannot read (that page is dropped from the cache, so the next run asks for it once more instead of keeping a non-card page). Such a run is **incomplete**: it reports why and writes nothing. A dry run fetches the package list and listings only (they may land in the page cache) and no detail pages.

**Plan.**
- *Shape check.* A listed printing id that does not match `PrintingId`, and a detail page whose card number does not match `CardNumber` (or its printing id), or whose TYPE, COLOR or rarity is not in the closed vocabularies (`CardKind`, `Color`, `Rarity` through the existing `parse_kind`/`parse_color`/`parse_rarity`), is rejected: reported with what and why, and left out of the build, so it is never stored. When a card's base printing page is rejected, all of that card's pages are left out of the build, so a stored card keeps its stored data. The rest of the run goes on.
- *Packages.* Each Bandai package that has a Bandai package id and a code that is in neither the tracked `sets.json` nor the dataset's provisional list is recorded as **provisional** (Bandai's name, code, kind, package id and release date when Bandai gives one; Bandai wins on dates). Provisional packages live in the dataset, `$GCG_DATA_DIR/gundam_cards/provisional_sets.json` (a `SetsFile`); an entry not in `sets.json` is kept up to date from Bandai and never removed. `sets.json` is only read. `store.load_sets()` (every reader of sets) returns both, and when a code is in both the `sets.json` entry wins; promotion into `sets.json` stays a manual step.
- *Cards and printings (reprints by card number).* The catalog is rebuilt the way `reparse` builds it, from the cached detail pages, but with each printing's packages taken from this run's listings. A printing id that several packages list carries all of them, so a reprint package that lists existing ids adds itself to those printings' packages; a new printing id of an existing number becomes a new printing of that card; only a number new to the catalog becomes a new card. A card's number and name come from its base printing page, which is never re-fetched, so a reprint cannot change them; its original set is the set its number belongs to, and the base printing keeps its `set_code`. The build merges into the stored catalog with the existing append-only `merge_catalog` (nothing removed, first-recorded kept, new cards dated now).
- *Missed once / no longer listed.* `CardRecord` gets `missed_once: bool = False` (old files read as not missed). Only a complete real run counts misses: the "listed" set is the card numbers of every valid printing id on the listings. A stored card that is not listed and not yet marked is a miss: the first miss sets `missed_once`; a miss on a card already `missed_once` sets `no_longer_listed`. A listed card clears both. `merge_catalog` takes this listed set; without one (the existing `reparse`, which has no listings) it keeps every stored card's marks as they are, so `no_longer_listed` is now set only by two consecutive complete refreshes.
- *Anomaly guard.* "Existing cards" are stored cards not marked no longer listed. A card counts as **dropped** when this run misses it (first or second miss), and as **changed** when its rebuilt data differs from its stored data in anything other than its printings, text-version list and fetch time (so its name, kind, stats, traits, keywords, link, FAQ or current wording changed; gaining a printing or a package is not a change). The run is refused when `(dropped + changed) / existing > ANOMALY_SHARE` (0.02, the owner's choice: more than 1 card in 50), unless `--allow-anomaly` is given; the report gives both counts, the total and the threshold. With no existing cards the guard never refuses.

**Write.** Only after a complete, accepted, non-dry run, back to back: `cards.json` first, then the derived `traits.json` and `source_titles.json` (as today), and `provisional_sets.json` when its content changed. Each goes through `write_atomic` (a temporary file in the same folder, renamed over the old one, removed on any error or interruption), so no file is ever left partly written. The catalog's `generated_at` is the refresh time (it is what `status` reports), so a re-run with the same listings rewrites only that stamp: cards, records and provisional packages stay equal. The dry run stops after the plan and reports the provisional packages it would record, the packages with new printings (provisional or known), the new card numbers and printing ids, the cards it would count as missed (and which would be marked), and the guard's verdict.

Why this over the obvious alternative (extending `sync`): `sync` writes the tracked `sets.json`, fetches detail pages even when a listing fails and writes partial results; the refresh's guarantees (all or nothing, nothing tracked) are easier to hold in one function with a separate write phase. `sync`, `reparse` and `refetch` stay as they are (except that `reparse` no longer marks cards).

## Files and interfaces
- `tools/gundam_cards/refresh.py` (new): `ANOMALY_SHARE = 0.02`; `Rejected(subject, reason)`; `RefreshReport` (complete, failure, provisional packages, packages with new printings, new cards, new printings, missed, marked, dropped/changed counts, existing, refused, rejected, issues, written); `refresh_catalog(fetcher: TextFetcher, raw_dir: Path, *, tracked_dir: Path = OUT_DIR, out_dir: Path | None = None, dry_run: bool = False, allow_anomaly: bool = False, now: datetime | None = None, progress=...) -> RefreshReport`; `shape_problems(page: SourcePage) -> list[str]`.
- `tools/gundam_cards/sets.py`: `fetch_package_list(fetcher: TextFetcher) -> tuple[tuple[PackageEntry, ...], tuple[RawProduct, ...]]`, used by `sync_sets` (which takes a `TextFetcher`).
- `tools/gundam_cards/printings.py`: `parse_card_list_raw(html) -> tuple[str, ...]` (ids as written, for the shape check); `parse_card_list` built on it.
- `tools/gundam_cards/models.py`: `CardRecord.missed_once: bool = False`.
- `tools/gundam_cards/store.py`: `merge_catalog(..., listed: frozenset[CardNumber] | None = None)`; `write_catalog(..., listed=None)` split into the merge and `save_catalog(cards: CardsFile, out_dir=None)`; `load_source_pages(raw_dir, packages_of=None)`; `load_tracked_sets(out_dir=OUT_DIR)`, `load_provisional_sets(out_dir=None)`, `write_provisional_sets(sets, generated_at, out_dir=None) -> bool`; `load_sets()` returns tracked plus provisional, tracked winning.
- `tools/gundam_cards/cli.py`: `refresh` subcommand (`--dry-run`, `--allow-anomaly`), `refresh_fetcher() -> Fetcher` (interval 0.5 s, default User-Agent). Exit 0 when written or a clean dry run, 1 when incomplete or refused.
- `shared/test_empty_dataset.py`: `refresh` listed as a network fetch.
- `docs/glossary.md`: provisional package, no longer listed.
- Docs: `tools/gundam_cards/design.md` (refresh, provisional packages, missed once), `docs/commands.md`, `docs/tuning.md` (`ANOMALY_SHARE`).

## Tests
All with a fake fetcher (records every request, writes the page cache like the real one) and small synthetic pages; no network.
- AC-1 (`tools/gundam_cards/tests/test_catalog_refresh.py`): a first refresh with no hand-entered data creates the catalog from Bandai's package list and listings; a package missing from `sets.json` is recorded as provisional with Bandai's name, code and release date and its cards are crawled; a package Bandai gives no release date for is recorded with none and still crawled; `load_sets()` returns it, and for a code in both sources returns the `sets.json` entry; the tracked sets file is byte-identical. A second refresh adds a new card with its first-recorded date and a new printing to an existing card; every earlier card is kept, nothing duplicated, the count does not drop. A run against the real tracked folder (`OUT_DIR`) leaves `git status --porcelain` unchanged (skipped outside git).
- AC-2: a reprint package listing only existing numbers (new printing ids) is itself recorded (provisional, readable through `load_sets`) and adds one printing per card recording the new package, no new card, and number, name and base printing's set unchanged; a package listing existing printing ids adds the package to those printings without duplicating them; a mixed package adds printings to existing numbers and cards only for new numbers; re-running with the same listings leaves cards, records and provisional packages equal.
- AC-3: one complete miss sets `missed_once` and nothing visible (`no_longer_listed` false, card kept); a second consecutive complete miss marks it; a card that reappears after one miss has its miss cleared, and after being marked is listed again; an incomplete run (a listing fails) leaves `missed_once`/marks unchanged and writes nothing. `test_catalog_history.py` updated: a rebuild without listings keeps cards and no longer marks them.
- AC-4: (a) a listing with a malformed printing id and detail pages with an unknown TYPE, COLOR or rarity, or a mismatched card number: each rejected and reported with a reason, absent from the stored catalog, the valid cards stored; (b) a run where more than 2% of existing cards would be dropped or changed is refused with the counts and leaves the dataset byte-identical, and with `allow_anomaly` it writes; the boundary: exactly 2% (1 of 50) is written, just over (1 of 49) is refused; through `cli.main`, a refused `refresh` exits 1 and writes nothing, and `refresh --allow-anomaly` exits 0 and writes; (c) a failed or unreadable package list, a failed listing, an unreadable (empty) listing, a failed detail fetch, an unreadable detail page and a `KeyboardInterrupt` at the package list, at a listing or during detail fetching each leave every file in the dataset byte-identical; an interruption at each of the write phase's writes, before its rename or halfway through writing it, leaves every file either its old bytes or a whole new file (no stray temporary file), `cards.json` changed only once its own write finished, and the next run brings the derived files level with `cards.json`.
- AC-5: a second run with nothing new requests only the package-list pages and listings (no detail URL), and never re-requests a cached detail page; every request goes through one fetcher, sequentially; `cli.refresh_fetcher()` is a `Fetcher` with interval >= 0.5 s and the default User-Agent, and a request it makes to a local server carries that User-Agent header (spacing, and the header on every request, are covered by `shared/test_fetch.py`); a dry run requests no detail page, leaves the dataset byte-identical, and reports provisional packages, new card numbers and printings, missed cards and the guard verdict, both "ok" and "would refuse" (also through `cli.main(["refresh", "--dry-run"])` with the fake fetcher).

## Risks
- **Anomaly threshold (0.02) is a judgment** (the owner lowered it from 0.10). A large reprint with errata could change many cards' current wording and be refused; the report gives the counts and `--allow-anomaly` lets the owner proceed. Recorded in `docs/tuning.md`.
- **"Fails to parse" is read as structurally unreadable** (`DetailPageError`) for a newly fetched page, which aborts the run. Finer build errors on a page (an unrecognized trait or link format, the existing `parse_failure` issues) keep today's behaviour: reported, that card left out of the build, a stored card keeping its stored data. Otherwise one odd card would block every refresh until the parser is fixed.
- **The write phase is not all-or-nothing across files** (the owner's decision, AC-4(c)). Everything is fetched and planned before the first write, so an interruption before the write phase writes nothing. The writes are up to four back-to-back atomic file writes, `cards.json` first and then the derived `traits.json`, `source_titles.json` and `provisional_sets.json`; an interruption during them may leave the derived files a refresh behind `cards.json`. The next run rewrites them from the catalog, so it repairs them. No file is ever partly written: each is written to a temporary file and renamed over the old one, and the temporary file is removed on an error or interruption.
- **The rebuild uses every cached detail page.** If a cached page of a printing that is no longer listed was deleted by hand, the card's rebuilt data loses that printing (the card itself is kept). Same as `reparse` today.
- **Dry-run "changed" count is from cached pages only**: a new printing that would change a card's current wording is not seen until it is fetched, so the dry-run verdict can differ from the real run's. The real run re-checks before writing.
- **`sync`/`reparse` still write `sets.json`.** They are the existing manual commands, out of scope here; the refresh never calls them.
